01 · Architecture Overview

One notification, six systems, one delivered push.

An Ops/Admin user creates a notification in iWorkBench. It's stored in MongoDB. A scheduler running every 15 minutes evaluates eligible notifications and sellers, resolves FCM tokens, publishes events to Kafka, and a CPaaS service consumes those events and calls Firebase FCM, which delivers the notification to the seller's device.

Authoring

iWorkBench is where an Ops/Admin defines what a notification says, who it's for, and when it's allowed to send. Nothing leaves this layer immediately — the notification is written to MongoDB in a pending state.

Scheduling

A scheduler polls MongoDB every 15 minutes, evaluates each pending notification's dynamic conditions, and resolves the FCM token for every eligible seller.

Delivery

Eligible seller/token pairs are published to Kafka. A CPaaS service consumes those events and sends an authenticated request to Firebase FCM, which routes to the device.

From admin action to device delivery.

The end-to-end sequence a single notification travels through in production.

Notification created in iWorkBench

The production scheduler reads notification records from MongoDB whose send window has opened and are still pending.

The scheduler evaluates each notification's targeting rules — category, region, seller tier, opt-in status — to build the eligible seller set. See condition types below.

Scheduler

For each eligible seller, the scheduler resolves the FCM token their mobile app most recently registered.

Scheduler

The scheduler publishes one notification event per seller/token pair to a Kafka topic, decoupling scheduling from delivery.

Kafka

The CPaaS notification service consumes events off Kafka and builds a platform-specific payload for each device.

CPaaS

The CPaaS service sends an OAuth 2.0 authenticated HTTP POST to the Firebase Cloud Messaging API for each device.

Firebase FCM

Notification delivered to device

Firebase routes the payload using the FCM token to the seller's mobile app, which renders the notification and handles the deep link on tap.

Mobile App
03 · FCM Token Registration Flow

How a device becomes reachable.

Before the scheduler can resolve a token, the mobile app has to register one. This runs independently of the send flow, whenever the app starts or its token refreshes.

A

App requests an FCM token

On launch (or when a token is refreshed), the mobile app asks the Firebase SDK for a current device token.

B

Token sent to the backend

The app sends the token, along with the seller's identity, to the token-registration endpoint.

C

Token mapped to seller

The backend stores the token against the seller's record, replacing any previous token for that device.

D

Available for the next scheduler cycle

The stored token is what the scheduler resolves in step 05 of the notification flow.

Why this matters

Token registration is what keeps delivery reliable. A stale or missing token is the most common reason a notification doesn't reach a device.

Tokens rotate. FCM may issue a new token for a device at any time, so the mobile app re-registers whenever Firebase reports a refresh.

05 · Dynamic Condition Overview

How eligibility is decided.

Each notification carries its own targeting rules. The scheduler evaluates these against every seller on every cycle to build that run's eligible set.

Audience

Category, region & tier

Restricts a notification to sellers matching a business category, geographic region, or account tier.

Lifecycle

Account status

Only active, verified sellers are considered — suspended or incomplete accounts are excluded automatically.

Engagement

Opt-in & preferences

Sellers who have opted out of a notification category are filtered out before token resolution.

Timing

Schedule window & time zone

A notification is only eligible while the current time falls inside its configured send window.

Throttling

Frequency caps

Per-seller sending limits prevent a single seller from receiving an excessive number of notifications in a short period.

06 · Kafka, CPaaS & Firebase FCM

Decoupled scheduling from delivery.

Publishing to Kafka lets the scheduler move on immediately, while a separately-scaled consumer handles the slower work of talking to Firebase.

Kafka

The scheduler publishes a notification event per eligible seller/token pair. Kafka buffers bursts and lets the CPaaS service consume at its own pace.

CPaaS Service

Consumes events, builds the platform-specific message body, and manages retries for transient delivery failures.

Firebase FCM

Receives an OAuth 2.0 authenticated request per device and routes the payload to the matching seller mobile app.
