01 · Architecture Overview

One notification, six systems, one delivered push.

An Ops/IworkBench user creates a notification in iWorkBench. It's stored in MongoDB. A scheduler running every 15 minutes evaluates eligible notifications and sellers, resolves FCM tokens, publishes events to Kafka, and a CPaaS service consumes those events and hit http_post method to firebase using fcm token and api_key for authentication, which delivers the notification to the seller's device.

Authoring

iWorkBench is where an Ops/IworkBench user defines what a notification says, who it's for, and when it's allowed to send. Nothing leaves this layer immediately — the notification is written to MongoDB in a pending state.

Scheduling

A scheduler polls MongoDB every 15 minutes, evaluates each pending notification's dynamic conditions, and resolves the FCM token for every eligible seller.

Delivery

Eligible seller/token pairs are published to Kafka. A CPaaS service consumes those events and sends an authenticated request to Firebase FCM, which routes to the device.

03 · FCM Token Registration Flow

How a device becomes reachable.

Before the scheduler can resolve a token, the mobile app has to register one. This runs independently of the send flow, whenever the app starts or its token refreshes.

A

App requests an FCM token

On launch (or when a token is refreshed), the mobile app asks the Firebase SDK for a current device token.

B

Token sent to the backend

The app sends the token, along with the seller's identity, to the token-registration endpoint.

C

Token mapped to seller

The backend stores the token against the seller's record, replacing any previous token for that device.

D

Available for the next scheduler cycle

The stored token is what the scheduler resolves in step 05 of the notification flow.

Why this matters

Token registration is what keeps delivery reliable. A stale or missing token is the most common reason a notification doesn't reach a device.

Tokens rotate. FCM may issue a new token for a device at any time, so the mobile app re-registers whenever Firebase reports a refresh.

06 · Kafka, CPaaS & Firebase FCM

Decoupled scheduling from delivery.

Publishing to Kafka lets the scheduler move on immediately, while a separately-scaled consumer handles the slower work of talking to Firebase.

Kafka

The scheduler publishes a notification event per eligible seller/token pair. Kafka buffers bursts and lets the CPaaS service consume at its own pace.

CPaaS Service

Consumes events, builds the platform-specific message body, and manages retries for transient delivery failures.

Firebase FCM

Receives an OAuth 2.0 authenticated request per device and routes the payload to the matching seller mobile app.
