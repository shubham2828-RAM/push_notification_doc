Protected Technical Documentation

Under the hood of the notification pipeline

Implementation detail behind the public overview — how events are shaped, how failures are handled, and how the system scales. This documents an existing production architecture; nothing on this page executes against it.

This is a documentation layer describing a live system. Values below (topic names, field names, thresholds) are illustrative of the design and simplified for presentation.
01 · Kafka Event Schema

What the scheduler publishes.

One event is published per eligible seller/token pair, keyed by seller ID so all events for a seller land on the same partition and preserve order.

seller.notifications.eventsJSON
{
  "eventId": "evt_9f2a1c",
  "notificationId": "ntf_5b8e2d",
  "sellerId": "slr_1029384",
  "fcmToken": "<device_token>",
  "title": "Payout ready to withdraw",
  "body": "Your July payout is available.",
  "deepLink": "app://payouts/summary",
  "priority": "HIGH",
  "createdAt": "2026-08-08T09:15:00Z"
}
PropertyNotes
eventIdUnique per publish; used for idempotency on consume.
sellerIdKafka partition key — keeps per-seller ordering.
fcmTokenResolved at publish time, not at consume time.
priorityMaps to FCM message priority (HIGH / NORMAL).

Topic design

A single topic with multiple partitions, sellerId as the partition key. Partition count is set to match the CPaaS consumer group size so every consumer instance stays busy.

02 · Reliability & Retry Policy

What happens when a send fails.

Delivery failures fall into two buckets: transient (retry) and terminal (don't retry).

Transient

Network timeouts, FCM rate limiting, and 5xx responses are retried with exponential backoff by the CPaaS consumer before the event is considered failed.

  • Bounded number of attempts per event
  • Backoff increases between attempts
  • Exhausted retries route to a dead-letter topic

Terminal

An FCM response indicating an invalid or unregistered token is not retried — it's treated as a signal to clean up stale state.

  • Unregistered token is removed from the seller's record
  • Event is marked failed on the notification's counters
  • No further attempts for that token
OutcomeHandling
Deliverednotification.delivered_count incremented.
Retried & deliveredCounted as delivered once an attempt succeeds.
Retries exhaustedRouted to dead-letter topic; notification.failed_count incremented.
Invalid tokenToken cleared from seller record; treated as failed, not retried.
03 · Scaling Notes

Handling large fan-out.

A single notification can target a large share of the seller base — the design assumes that as the normal case, not the exception.

Scheduler

Processes notifications independently, so a large notification doesn't block smaller ones from being evaluated in the same cycle.

Kafka partitions

Partition count is sized to the CPaaS consumer group so throughput scales roughly linearly with added consumers.

CPaaS consumers

Horizontally scaled; each consumer instance owns a subset of partitions and can be scaled up ahead of known high-volume sends.

04 · Security Notes

Keeping delivery credentials contained.

Auth

OAuth 2.0 service account

The CPaaS service authenticates to Firebase using a service account credential, not a long-lived static API key.

Secrets

Managed outside application code

Credentials are held in a secrets manager and injected at runtime — they are never checked into source or logs.

Access

Least-privilege topics

The scheduler can only publish to the notification topic; the CPaaS service can only consume from it.
